## Problem / Motivation

After reading the Stage 0 literature report, the owner set the project's real target on 2026-10-13:

- a local English and Turkish assistant for calendar, email and reminders;
- trained from scratch with volunteer compute;
- built under a strict data policy.

The owner also asked to stop spending laptop days on experiments that only test whether the concept works, and to build the networked system instead.

None of this was written down. `docs/PLAN.md` describes Stage 0 only, and the SRS outlines Stages 1 to 3 around the old premise.

## Implementation Approach

The roadmap records the plan discussed with the owner on 2026-10-13 and the four answers given that day:

- both work-unit kinds in network v1;
- a system study before choosing a framework;
- a small cloud server for the pilot coordinator;
- 3 to 5 trusted people for the pilot.

A second round of questions the same day, held at the owner's request with the advisor's review, replaced the cloud coordinator. The owner wants no server of ours (D37):

- **May stay central:** the signing key, bootstrap peers on the owner's and pilot participants' machines, public file hosts, and the published starting configuration.
- **Training:** asynchronous or group averaging, with a synchronous mode kept for comparisons with Stage 0 (D38).
- **Relays:** only our own machines.
- **Write access to shared state:** left to the system study.

The roadmap now:

- treats decentralization as the baseline;
- splits Gate N1 into a synchronous plumbing check (N1a) and a gate for the asynchronous algorithm (N1b);
- rescopes the system study;
- makes "at least 2 holders per expert" a requirement.

It keeps the old documents as records rather than rewriting them now. The SRS rewrite is its own step (1.4), so that it can draw on the system study and the product spec.

## Design Decisions

- **A new `docs/ROADMAP.md` rather than editing `docs/PLAN.md`.** PLAN.md is the record of Stage 0, cited by the report and the close-out. Rewriting it now would break those references. Step 1.4 decides whether PLAN.md is replaced or archived.
- **The infrastructure is kept separate from the training method** (principle 1). This follows D34 and the existing coordinator's design, which was kept free of simulation code for Stage 1.
- **The time estimates are labelled rough**, to be revised after Phase 1.
- **The asynchronous algorithm is not chosen here.** Stage 0 measured synchronous rounds, so asynchronous training is a different algorithm. Keeping the synchronous mode (D38) keeps Gate N1a and the batch-1 research pool comparable with Stage 0. The asynchronous algorithm gets its own gate (N1b), written down once the study names it.
- **The minimum of 2 holders per expert follows from the code, not from the literature.** Under `coverage`, an expert has a single holder in 29.6% of rounds (100,000 simulated draws of the assignment code; `docs/research/2026-10-11-literature-notes/audit/README.md`). Without a server, that holder disconnecting would lose the expert's update for the round.
